# Research: 010 shell auth

- **Token storage**. Decision: use `sessionStorage` (`pv.session`), falling back to memory. Rationale: this matches the legacy non-persistent Forms Authentication cookie, which was cleared when the browser closed. Each tab is its own session. Alternatives: `localStorage` (would outlive the browser like a persistent cookie, which legacy never set), and an httpOnly cookie (would need server changes and CSRF handling, out of scope since spec 004 fixed bearer tokens).
- **Expiry**. Decision: three paths lead to the "expired" sign-in. (a) The token `exp` has passed at load. (b) A timer fires at `exp`. (c) Any PV request returns 401. Rationale: tokens are stateless and HMAC-signed. The client reads `exp` only to expire early and never trusts it for authorisation.
- **Sign-out**. Decision: discard the token on the client and make no server call. Rationale: tokens are stateless (spec 004). Legacy `FormsAuthentication.SignOut` likewise only removed the cookie.
- **Role table location**. Decision: `src/model/pv/access.ts` holds the `PV_PAGES` rows in legacy nav order, with `screen: null` until the screen spec for that page lands. Rationale: there is one place to edit, and nav and gating cannot drift apart.
- **Harness without sign-in**. Decision: `?state=` always wins. Without a session, `Populated` renders the fixed slice `preview()` with a preview identity. Rationale: the harness must not depend on a database password, and output must be deterministic.
- **App-only visual coverage**. Decision: text assertions plus PNG baselines with a 0.5% tolerance, which is the same order as the existing mockup font-rendering noise. `/api/pv` responses are routed for the sign-in, forbidden, expired and sign-out flows. Rationale: there is no mockup to compare against, and routed responses keep the flows independent of DB state.
- **Demo passwords**. Decision: `PV_DEMO_PASSWORD=… npm run pv:demo-passwords` sets one synthetic password on every active seeded user. The password is read from the environment and is never committed, and the script refuses to run in production. The existing per-user `pv:set-password` is unchanged.
