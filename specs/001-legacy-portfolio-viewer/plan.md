# Implementation Plan: Legacy Portfolio Viewer Capabilities in Wealth Platform

**Branch**: `001-legacy-portfolio-viewer` | **Date**: 2026-10-12 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/001-legacy-portfolio-viewer/spec.md`

## Summary

Retire Portfolio Viewer (ASP.NET Web Forms + SQL Server + flat-file SWIFT archive) by adding a
**Custody** bounded context to Wealth Platform: a TypeScript SWIFT MT535/MT54x parser and
idempotent ingester that stores every raw message plus normalized statements/confirmations in
Oracle, `/api/custody/*` routes with typed DTOs, and six screens (holdings history, settlements,
position check, message browser, ingestion admin, client search) linked from Client 360 and the
operations workspace. Parity is proven against fixtures generated by running the legacy `PV.Core`
over the committed archive; four legacy defects (D-1..D-4) are fixed deliberately, with a
legacy-parity mode kept for sign-off. Approach details: [research.md](./research.md).

## Technical Context

**Language/Version**: TypeScript 5 (strict), Node.js 20 (repo runs v20.19); C# / .NET Framework 4.8
for the one-off legacy parity harness only

**Primary Dependencies**: Existing only — React 18, Vite, Express, `node-oracledb` (thin). Unit
tests use the built-in `node:test` runner via `tsx --test` (no new dependency)

**Storage**: Oracle (19c+ compatible SQL; Oracle Free 23 container for tests) — new `custody_*`
tables in `server/db/schema.sql`; legacy SQL Server reference data and archive files are one-off
migration inputs

**Testing**: `node:test` unit tests (parser, effective-statement, cancellation, reconciliation);
parity tests against committed JSON fixtures; `npm run typecheck`, `npm run build`,
`npm run visual-diff` for screens; Oracle container for ingestion integration test

**Target Platform**: Existing Wealth Platform web app (browser + Express API)

**Project Type**: Web application (single repo: `src/` frontend, `server/` API)

**Performance Goals**: Full archive (6,044 files) ingested in < 2 min; incremental re-ingest of an
unchanged archive < 15 s; custody screens < 2 s (SC-006)

**Constraints**: Raw messages immutable and byte-preserved; no domain data in the browser; role
checks server-side; legacy-parity numbers reproducible from committed fixtures

**Scale/Scope**: 50 clients, 120 accounts, 302 instruments, ~31k holding lines, ~3k confirmations,
+~90 statements/week; 6 user stories, ~12 endpoints, 6 screens

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

| Principle | Gate | Status |
|---|---|---|
| I. Oracle is system of record | All custody data in Oracle via `server/repositories/custody.ts`; screens use `src/api/client.ts` | PASS |
| II. Typed wire contracts | DTOs in `src/api/types.ts` ([contracts/api.md](./contracts/api.md)); `Currency` widened deliberately to add `GBP`, `EUR`; account types a closed union | PASS (widening justified in research R-3) |
| III. Parity before replacement | As-built spec + legacy-generated fixtures before any screen; deviations listed as **[fix D-n]** | PASS |
| IV. Auditable records | `custody_messages` immutable with hash/provenance; RPLC/DUPL/CANC as new rows; `custody_break_note_history` append-only | PASS |
| V. Deterministic verification | Schema re-runnable; small custody seed in `seed.sql`; full archive load only in integration test; parser tests DB-free | PASS |
| Security constraints | Role middleware on API; no legacy hashes; messages by id, escaped render | PASS with interim simulated identity (Complexity Tracking) |

**Post-design re-check**: PASS — design artifacts introduce no new violations.

## Complexity Tracking

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| Simulated identity (`SIMULATED_AUTH=1`, user chosen via `?as=`) instead of real login | Platform has no auth yet; FR-022 needs server-side role checks to be testable now | Skipping role checks violates the security constraint; building SSO is a separate platform feature |
| Separate `custody_clients`/`custody_accounts` instead of reusing `clients`/`accounts` | Legacy accounts lack household, drift, target-weight data and `accounts.account_key` is `VARCHAR2(4)` `NR/RR/CO` | Forcing them into household tables would fabricate data and break existing DTOs; a later feature can link them via `custody_clients.platform_client_id` |
